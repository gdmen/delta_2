## Vision

Replace hand-coded dashboard surfaces (`/`, `/recovery`, `/body-comp`, `/sports/[sport]`) with a config-driven engine. DB-backed `dashboards` + `dashboard_widgets` tables. Single `/dashboards/[slug]` route. Drag-and-drop edit mode. Three system dashboards seed (Today, Recovery, Body Comp) — sport pages get deleted; users build their own (powerlifting, BJJ, etc.) via `+ New dashboard`.

The strategic driver is multi-user (real, within 6 months). Building the abstraction + editor now means multi-user lands without a parallel dashboard build.

### E4 contract (was underspecified)

```ts
type ValidationResult =
  | { ok: true }
  | { ok: false; reason: string; severity: 'error' | 'warning'; canEdit: boolean };

type WidgetDef<P> = {
  // ... existing fields ...
  validate?: (config: P, ctx: { db: DrizzleDb }) => Promise<ValidationResult>;
};
```

`ctx.db` is the Drizzle handle (same one route handlers use, imported from `@/db`). Validation runs server-side at render time, before data fetch. On `ok: false`, the widget slot renders a typed error state with the `reason` text and (if `canEdit`) a button that opens the settings drawer pre-loaded with this widget's config.

## UX edge case additions (raised in Section 4)

- **PR1:** `collectDataDeps` uses `Promise.allSettled`, not `Promise.all`. One failed data fetch renders that widget's error boundary; the rest render normally.
- **PR3:** Autosave is debounced 500ms for prop edits in the settings drawer. Add/delete/drag/resize fire immediately. A per-widget mutation queue (in-flight + pending) ensures out-of-order writes can't happen.
- **PR3:** Settings drawer auto-closes if its underlying widget is deleted from elsewhere.
- **PR3:** Settings drawer warns on browser-back / route change with unsaved draft props (or autosaves on close — implementer's call).
- **PR4:** "+ New dashboard" button disables during the in-flight POST. Re-enables on response (success or error).
- **PR4:** Soft cap of 30 widgets per dashboard. Adding past the cap shows toast: "Dashboards work best under 30 widgets. Consider splitting into two dashboards."

## Security additions (raised in Section 3)

- **PR2:** `text_card` widget renders through `react-markdown` + `rehype-sanitize`. HTML tags stripped at render time. Links and images allowed. Eliminates stored XSS exposure ahead of multi-user.
- **PR4:** `slug` validation Zod schema: `/^[a-z0-9][a-z0-9-]{0,63}$/` plus reserved-name list (`api`, `_next`, `dashboards`, `data`, `goals`, `data-sources`, `input`, `recovery`, `body-comp`). Auto-generate from `name` if not provided. Rejected on create/rename with a clear error.
- **All mutation routes:** standard Zod input validation already covered in Section 2 (per-route schemas, 400 with reason on failure). Bounds: `grid_x ∈ [0,11]`, `grid_w ∈ [1,12]`, `grid_y >= 0`, `grid_h ∈ [1,50]`. `name` max 255, `icon` max 32. `config` JSON max 4KB.

## Error rescue additions (raised in Section 2)

All four added to the plan:

- **PR1:** `<WidgetSlot>` wraps every widget render in an error boundary that catches both `validate()` failures and `Component` render failures. Renders "This widget failed to render" with edit/delete buttons.
- **PR3:** Every mutation route validates payloads against a Zod schema (widget config schema for widget mutations, layout schema for batch layout updates). 400 with `{ reason }` on validation failure. Editor surfaces toast.
- **PR3:** Autosave fetch checks for 401 response → calls `window.location.reload()` rather than silently dropping the mutation. The basic-auth re-prompt pattern lets the user re-enter password and continue.
- **PR3:** The live preview pane in the settings drawer has its own error boundary independent of the main grid. A draft config that crashes only shows "Preview unavailable" inside the drawer; main dashboard keeps rendering.

Effort: ~1h CC total across the three PRs.

## Responsive units (no pixels) — supersedes RGL choice

**User directive:** the dashboard UI must be fully responsive. No pixel sizing for layout, typography, or widget heights. Pixels reserved for things that have to be pixels (1px borders, hairline dividers, 1px focus rings).

This kills react-grid-layout as the primary path. RGL's `rowHeight` prop is `number` (pixels) and its drag/resize math is pixel-based. Pivot:

**Layout: pure CSS Grid + dnd-kit.**

- The dashboard renders as a CSS Grid with `grid-template-columns: repeat(12, 1fr)` (12 columns, each 1 fractional unit of available width). Container width inherits from page, which is bounded by `max-width: 75rem` on desktop and `100%` below the lg breakpoint.
- Each widget cell uses `grid-column: span N` (where N comes from `grid_w`) and `grid-row: span N` (where N comes from `grid_h`).
- Row height is `grid-auto-rows: minmax(8rem, auto)` — minimum 8rem, expand to widget content. No fixed row height. Widgets that need more vertical space (charts, lists) just take it via `grid_h`.
- Gaps: `gap: 1rem` between widgets. Bumps to `gap: 1.5rem` at lg breakpoint.
- Drag/resize: `@dnd-kit/core` for drag (sortable preset for reordering), custom resize handle that mutates `grid_w`/`grid_h` integers. dnd-kit is already React 19 clean and unit-agnostic — it returns drag deltas you can interpret in grid units.
- Mobile (`< sm` breakpoint): grid collapses to `grid-template-columns: 1fr` (single column). Widgets render in `position` order, full width, `grid-row: span 1`. Drag-resize disabled; edit mode shows vertical reorder list (existing plan).

**Schema implication: `grid_w/grid_h` are abstract grid units, not pixels.** This was already true in the schema; making it explicit. Bounds stay `grid_x ∈ [0,11]`, `grid_w ∈ [1,12]`, `grid_h ∈ [1,50]`. No conversion to pixels at render time — the CSS Grid handles sizing.

**Typography & spacing:**

- All font sizes in `rem`. Body 1rem, scale up via design system (e.g., `0.75rem`, `0.875rem`, `1rem`, `1.125rem`, `1.5rem`).
- All paddings, margins, gaps in `rem` (or `em` when font-relative is correct).
- Border widths in pixels (1px, 2px) — pixel borders look correct at every zoom level. Border-radius in `rem`.
- Shadow blur radii in `rem`.
- Existing `globals.css` and Tailwind config audit: PR1 includes a quick pass to flag any `px` values in shared layout primitives. Existing components (`MetricsStrip`, `MetricBlock`, etc.) already use Tailwind class-based sizing which compiles to `rem` by default. Sidebar widths and current `max-w-[1200px]` (= 75rem) get a tiny audit but probably stay as Tailwind classes since Tailwind's default sizing scale is rem-based.

**Breakpoints:**

- Use Tailwind's defaults expressed in rem (sm: 40rem, md: 48rem, lg: 64rem, xl: 80rem, 2xl: 96rem). Tailwind already uses these by default.
- Container queries (`@container`) where a widget's appearance should respond to its own size, not viewport. Example: a `metric_block` at `grid_w=3` shows axis labels every 2nd tick, but at `grid_w=12` shows every tick. Worth using container queries for chart widgets so they look right regardless of dashboard layout.
- Small caveat: container queries require all chart widgets' parents to set `container-type: inline-size`. Add to `<WidgetSlot>`.

**Drag/resize UX:**

- Drag: `@dnd-kit/core` `useSortable` per widget; drag preview shows the widget translated. On drop, the editor mutates the local layout state (grid_x/y of all affected widgets) and fires the autosave PATCH.
- Resize: hover-revealed handle on bottom-right corner of each widget in edit mode. Click-and-drag the handle. Handler measures pointer delta in pixels (yes, pixels — pointer events ARE pixel-based), divides by current cell size to convert to grid units, snaps to integer increments. Layout state updates locally.
- Edge case: dragging a widget into an occupied slot. dnd-kit's sortable preset auto-shifts adjacent widgets; that's the existing behavior.
- Keyboard: dnd-kit ships keyboard support via `KeyboardSensor`. Tab to a widget, Space to pick it up, arrow keys to move, Space to drop. Free a11y win that RGL doesn't have.

**Spike updated (PR1 first task, ~2h):**

- Mount `@dnd-kit/core` with `useSortable`. Verify drag works on desktop.

## Outside Voice Findings (resolved)

Outside voice surfaced 9 issues. All resolved as follows:

1. **RGL React 19 spike → first hour of PR1** (not PR3). Schema is shaped by RGL conventions; if RGL is broken on React 19, evaluate `@dnd-kit/core` + custom grid before committing the migration. Spike: install RGL, mount 3-widget test grid, drag/resize, check warnings. Decision in <1h.
2. **Multi-user-first reordering: declined.** Stay the course. When multi-user starts, retrofit `user_id INTEGER NOT NULL DEFAULT 1` on dashboards/dashboard_widgets via ALTER TABLE migration + WHERE clause additions. ~1 day CC retrofit. The 3-6 months of editor dogfooding before that is worth more than the retrofit cost.
3. **ZodForm UI metadata layer.** Each widget def carries `{ schema, uiMeta }`. `uiMeta` per field: `{ label, helpText, component (e.g. 'metric-picker', 'number', 'text', 'select') }`. Generic `<ZodForm>` reads both. Real auto-gen with proper labels and pickers. ~3-4h infrastructure in PR3, paid back across 11 widgets.
4. **`router.refresh()` removed from autosave hot path.** Editor maintains local state for layout + widget configs. Autosave fires PATCH but does NOT trigger refresh. Refresh only on (a) widget add/delete that changes data deps, (b) exit-edit-mode (`?edit=0`). For drag/resize/settings prop changes, local state is source of truth until exit.
5. **Error boundary split: server try/catch + Client error boundary, both layers, every render.** `WidgetSlot` (Server) wraps schema parse + `validate()` in server-side try/catch (catches sync errors before React traversal). It then renders the widget Component inside `<WidgetClientBoundary>`, a thin Client class component that catches Component render-time throws — which a server try/catch can't reach because ReactElement creation doesn't throw, only React's traversal does. Edit-mode (PR3) reuses the same Client boundary. Resolves the "RSC error boundaries don't catch server throws" gap.
6. **PR sequencing reordered: PR1 (renderer) → PR2 (CRUD + create dashboard) → PR3 (editor) → PR4 (delete old routes).** Always have a way to view + create dashboards before deleting hand-coded ones. New numbering used throughout this plan.
7. **`seeded_id` column for idempotent re-seeding.** New column `dashboards.seeded_id TEXT UNIQUE` (NULL for user-created). Seed migrations INSERT OR IGNORE on `seeded_id` (e.g. `'system:today'`), not on `slug`. User can rename freely; migrations stay idempotent.
8. **`text_card` body in dedicated column.** New column `dashboard_widgets.body TEXT` (NULL except for `text_card` widgets). Keeps `config` JSON tight (4KB cap stands); text_card body unconstrained.
9. **Per-widget `<Suspense>` streaming → deferred to TODOS.md.** v1 ships Promise.allSettled. Add Suspense streaming when slow widgets (coach_card LLM, etc.) make wait visible. Purely additive later.

## Auth note (raised during review)

Mutation endpoints (`POST/PATCH/DELETE /api/dashboards/...`) inherit the existing site-wide HTTP Basic Auth gate at `src/proxy.ts` (env: `SITE_PASSWORD`). When `SITE_PASSWORD` is set in production, the dashboard mutation routes are gated like every other non-`/api/ingest/*` route. No additional auth code needed for the single-user-pre-multi-user period. Multi-user will replace the binary gate with per-user scoping.

Design also accepts a "single-session" assumption: concurrent edits in two tabs/sessions silently last-write-wins. Documented as known limitation; not engineered around. If the user opens Delta in two tabs and clobbers their own dashboard, that is on them.

### Responsive + accessibility (Pass 6)

**Drawer behavior across breakpoints:**

- `≥ sm` (40rem): right-slide drawer. Width 24rem (palette) or 36rem (settings).
- `< sm`: bottom sheet. Slides from bottom, ~70vh tall, has visible 1rem-wide drag handle at top center. Swipe-down or tap backdrop closes.

Implement as `<Drawer side='right' | 'bottom-sheet'>` with breakpoint-driven side prop.

**Keyboard navigation:**
- Widgets are `<article>` elements. In edit mode: `tabindex={0}`. In view mode: undefined.
- Tab cycles widgets in DOM order (matches `position` then grid_y/x).
- In edit mode: Space picks up widget for keyboard drag (dnd-kit `KeyboardSensor`). Arrow keys move in grid units. Space drops, Escape cancels.
- Settings drawer opens with focus on first input. Escape closes.
- Modal traps focus while open. Escape closes (only if no unsaved state, otherwise prompts).

**ARIA:**
- Sidebar: `<nav aria-label="Dashboards">`
- Each widget: `<article role="region" aria-label="{widget title}">`
- Settings drawer: `<dialog aria-label="Edit {widget type}">`
- Widget palette: `<dialog aria-label="Add widget">`
- New dashboard / delete confirm: `<dialog aria-modal="true" aria-labelledby="dialog-title">`
- "Saved" pip: `<output role="status" aria-live="polite">`
- Mutation announcements (added/removed/moved/error) → aria-live="polite" region near top of main.

**Touch targets (mobile):** drag handles, gear, delete = 44×44px minimum. Sidebar items = 44px tall.

**Color contrast:** verified all text colors against backgrounds at WCAG AA. `--color-text-tertiary` (#737373) clears 4.5:1 just barely; reserve for tertiary muted text only. `--color-accent-red` (#ef4444) is 4.0:1 on white — use only for icons/dots, not body copy. Error body copy uses `--color-foreground`.

**Focus indicators:** all interactive elements get a 2px outline + 2px outline-offset using `--color-foreground`. Never disabled.

**Reduced motion:** drawer animations, "Saved" pip fade, drag preview transforms all respect `prefers-reduced-motion: reduce` → instant on/off.

### Resolved decisions (Pass 7)

- **System dashboard delete:** Delete button hidden entirely on `is_system=1` rows. Settings menu doesn't show it. No tooltip, no error toast.
- **Widget delete confirmation:** one-click delete + 5s "Widget removed. Undo" toast (top-right, primary action). Past 5s, gone. No modal.
- **Dashboard delete confirmation:** modal — "Delete '{name}'? This will remove {N} widgets. This can't be undone. [Cancel] [Delete]". Delete button uses `--color-accent-red` text on the modal CTA.
- **Mobile edit mode:** compact reorder rows. Each widget = one 44-56px tall row: drag handle (44×44px hit target, left) + 16px line icon + widget title (Inter Medium 0.875rem) + small type badge (e.g. "Metric chart" in muted) + gear (44×44px, right) + trash (44×44px, far right). Tap row body opens settings drawer (bottom sheet). dnd-kit `useSortable` provides reorder mechanics.
- **Empty-state CTA on new dashboard:** centered in the dashboard area below the title bar. Primary button styling (foreground bg, background text — matches Delta's existing button style). Above the button: muted text "This dashboard is empty." Icon optional, NOT decorative — use the same line icon as the palette's "+" indicator if any.
- **Widget palette icons:** line-style monochrome, 16px, no circles, no fills.

### Edit-mode visual signal

In edit mode, the dashboard differs from view mode in three ways:
1. Hairline outline on every widget (`outline: 1px solid var(--color-border)`).
2. Toolbar shows "+ Add widget" pill + "Done" pill instead of "Edit" link.
3. Hover-revealed handles (drag, gear, resize) appear on each widget.

No hatched backdrop, no status pill, no color-tinted background. The treatment is restrained.
